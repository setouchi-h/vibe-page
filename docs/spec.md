## Problem Statement

ChatGPT / Claude Code / v0 などのAIツールでHTML/CSS/JSを生成した非エンジニアが、それをWeb上で公開・共有・更新できない。Netlify Drop / Vercel / Cloudflare Pages / GitHub Pages は技術的には可能だが、index.html、フォルダ構成、相対パス、git、公開範囲、エラー対応などで詰む。結果として「AIで作ったが見せられない」「誰かエンジニアに代行を頼まないと更新できない」状態に陥る。

このプロジェクトの目的は、その「AIユーザーが自分で公開・更新できる最短経路」を提供すること。技術代替ではなく、UX代替。

## Demand Evidence

- **N=1（具体・確認済み）：** 創業者の同僚。AIで会社ホームページを作成したが、git/技術を知らないため公開できず、創業者が代理でGitHub Pagesを運用している。
- **月次の継続コスト：** 同僚から小さな修正・コピー変更依頼が月に何回か発生し、創業者が手動デプロイで対応している。これは「人間が払う形の需要」（時間コストでのworkaround）。
- **TAMの広がり証拠は未確認：** 「AIでHTMLを作る人」「公開で詰まる人」が同僚以外にどれだけいるかは検証されていない。最初のpost-launchアクションでこのN=1を超える必要がある。

これは「AIで作ったが見せられない」ペインの実例 N=1。少ないが、創業者自身が現状の人間ワークアラウンドである点が重要なシグナル（YC的に founder-as-the-workaround）。

## Status Quo

- 同僚は HTML を AI に作らせる → 創業者に渡す → 創業者が GitHub Pages へデプロイ → 更新依頼が来るたびに同上を繰り返す。
- 創業者の手動コストは月に複数回。
- 同僚は「自分で更新する手段」を持っていないため、創業者がボトルネックになっている。

## Target User & Narrowest Wedge

**ターゲット：** AIツール（Claude Code / ChatGPT / v0 等）でHTMLを生成したが、git/サーバー知識がないため公開・更新できない非エンジニア。

**Narrowest Wedge（最小機能）：**

1. HTMLを貼る、またはZIPをドロップ
2. 公開URL `xxx.example.com/{slug}` が発行される
3. **秘密の編集URL** `xxx.example.com/{slug}/edit?key=xyz` が発行される（同じ場所を何度でも上書きできる）
4. `index.html` 自動検出と相対パスの維持
5. 編集URLからの自分での削除

この4-5機能 **以外** は最初のMVPには入れない。**24h自動削除トグルは入れない**（P2に従う、長期保持のみ）。

**「最小」の妥当性確認：** 同僚さんが来週この機能で会社ホームページを公開・更新できる、が成功条件。

## Technical Specifications（着手前に確定）

実装者が質問なしで着手できるパラメータ。これが未定義のまま始めると2日分溶ける。

**Slug：**

- 6文字 base32 ランダム（`[a-z2-7]{6}`、約10億パターン）
- 衝突時は1回再生成、3回連続衝突なら 7文字へフォールバック
- ユーザー指定不可（MVPでは）

**Edit Token：**

- 128-bit ランダム（`crypto.getRandomValues` 由来）、URL-safe base64 エンコード約22文字
- URLに埋め込み発行（`/{slug}/edit?key=xxxxx`）
- KVには `slug → { tokenHash: sha256(token), createdAt, ... }` を保存。**平文保管しない**
- 復旧手段なし（MVP）。失った場合は別slugで作り直し

**Delete 権限：** 編集URL（同じトークン）を知っていれば削除可能。別トークンは不要。

**ZIP/ペースト制約：**

- 単一HTMLペースト：最大 500KB（テキスト）
- ZIPアップロード：圧縮後 10MB / 展開後 30MB / 100ファイル
- 許可拡張子（allowlist）：`.html .htm .css .js .png .jpg .jpeg .gif .svg .webp .ico .woff .woff2 .ttf .json .txt`
- 上記以外を含むZIPは全体を拒否
- 実行系（`.php .py .sh .exe` 等）は拒否

**index.html 検出：**

- ZIPルートに `index.html` があればそれを使用
- ない場合：唯一の `.html` ファイルがあればそれをルートに昇格、それ以外なら拒否（エラー：「`index.html` が見つかりません」）
- サブディレクトリの `index.html` は **そのサブパスでアクセス可能**（`/{slug}/about/` → `about/index.html`）

**Storage Layout：**

- R2 キー：`sites/{slug}/{original-path-in-zip}`
- KV：`site:{slug}` → `{ tokenHash, createdAt, updatedAt, fileCount, totalBytes }`
- KV：`ratelimit:{ip}` → カウンタ（TTL 60秒）

**ZIP 展開場所：** **クライアント側JS** で展開し、各ファイルを Workers 経由で個別に PUT。Workers 内で展開すると CPU 時間・sub-request 50 制限（無料プラン）に引っかかる。クライアント側展開なら `jszip` ライブラリ1つで済む。

**Content-Type：** 拡張子→MIME マッピング表を Workers に持つ。一覧は許可拡張子と同じ。不明な場合は `application/octet-stream`。

**Caching：** MVP では R2 直読み、CDN キャッシュなし。トラフィック増加後に Cache API で `slug` 単位キャッシュを追加。

**Consistency：** KV は eventually consistent。編集直後の閲覧で古いコンテンツが返る可能性あり（数秒〜数十秒）。MVP では許容、ToS に明記。

**Subdomain isolation（将来課題）：** `*.workers.dev/{slug}` で配信すると localStorage / cookie が全サイト共有。MVP では問題化しにくいが、AIが生成するJSがログイン的なことをやるとリスク。Phase 2 でユーザー固有サブドメイン化を検討（メモ）。

## abuse対策の最低ライン（MVP launch時）

「最低ライン」を曖昧にしないため、以下を **launch時の必須セット** として固定する：

1. **拡張子allowlist**（上記参照、実行系拒否）
2. **サイズ上限**（ZIP圧縮10MB、展開30MB、ファイル数100、単一HTMLペースト500KB）
3. **Rate limit**：IP単位、サイト作成 10/時間、ファイルアップロード 100/時間
4. **robots.txt = `Disallow: /`** を全サイトにデフォルト適用（検索インデックス防止）
5. **通報リンク**：全公開サイトのフッターに小さく「報告」ボタン、メールに飛ばす
6. **管理者削除画面**：創業者がslug指定で即削除できる管理用URL（パスワード保護）
7. **サイト一覧の非公開**：作成されたslug一覧を公開しない（discoverability ゼロ）

これ以外（マルウェアスキャン、フィッシング検知、コンテンツモデレーション）は同僚unblock後に追加。

## 初日 TODO（着手1時間以内に潰すこと）

レビュアーが指摘した「実装着手を止めないが初日に潰すべき」項目：

1. **Referrer-Policy ヘッダ：** 編集画面およびその遷移先で `Referrer-Policy: no-referrer` を設定。編集URLがログ・他サイト・スクショ経由で漏れるリスクを下げる
2. **管理者画面の認証：** Cloudflare Workers Secrets で管理者パスワード/トークンを管理。平文・環境変数は使わない
3. **robots.txt の配信経路：** Workers 側で `/{slug}/robots.txt` を動的に `Disallow: /` で返す。ZIPに `robots.txt` が含まれていても Workers が上書き
4. **編集完了画面に「反映まで数秒かかる場合あり」を表示：** KV eventual consistency 由来の体感不整合に対するサポート問い合わせを減らす

## Constraints

- 創業者は1人（または小規模チーム）。週末ビルド可能な規模であること。
- 同僚さんを来週unblockしたい、つまり開発期間は3〜5日。
- インフラ予算は月数千円レベル（個人開発）。
- 法的責任を最小化するため、abuse対策の最低ラインは確保する必要あり。

## Premises（合意済み）

1. **P1.** 唯一の実証された需要は「git/技術を知らない非エンジニアが、AIで作ったHTML/CSSを公開・更新したい」。具体的には創業者の同僚1人。それ以外はまだ推測。
2. **P2.** 24時間自動削除（一時共有）と同僚のユースケース（長期保持の会社HP）は両立しない。同じ製品で両方を訴求するとポジショニングが弱まる。MVPでは長期保持側を取る。
3. **P3.** Netlify Drop / Vercel / Cloudflare Pages / GitHub Pages は技術的には完璧だが、非エンジニアにとってのUXは破綻している。差別化軸は **非エンジニア向けUXの徹底**、技術差別化ではない。
4. **P4.** MVPの成功基準は「同僚さんが今週から自分で更新できる」。その他（abuse対策、自動削除、画像最適化、独自ドメイン）は同僚unblock後に追加。
5. **P5（Codex反論を採用・修正後）：** ターゲットは **AIユーザー**（Claude Code / v0 / ChatGPT で HTML を作っている人）。AIは単なるマーケフックではなく、**獲得チャネルとUX設計の中心軸**。「Claude Codeで作ったものを貼る」をコアコピーにする。ノンエンジニア一般（デザイナー、学生）は副次的TAM、最初は取りに行かない。

## Cross-Model Perspective（Codex独立読み）

- **Steelman：** 「AIで作ったHTMLを、非エンジニアが"そのまま貼るだけ"で公開・更新できる最小の静的サイト公開ツール」。Netlifyの技術代替ではなく、GitHub Pages担当者になっている社内エンジニアを外すための"非エンジニア向け公開ボタン"。
- **Codexのキー洞察：** 「月次で小さな修正・文言変更依頼が来て、創業者がGitHub Pagesで代行している」が一番重要なシグナル。これは「共有URLが欲しい」ではなく「**更新のたびに人間のデプロイ係が必要になる**」問題。だからMVPの核は一発公開ではなく、**本人が安全に上書き更新できること**。
- **CodexがP5を challenge：** 「AI-generated HTMLは単なるマーケフック」と言い切るのは早い。AIでHTMLを生成した人 **だけ** が高頻度に「次はどう公開する？」で詰まる可能性がある。→ 採用、P5を修正済み。
- **Codexの48時間プロトタイプ提案：** Cloudflare Workers + R2 + KV。HTML貼り付け、ZIPアップロード、URL発行、**秘密の編集URLで上書き**、`index.html` 自動検出、相対パス維持、削除ボタン。24h削除はトグル任意、デフォルト永続。アカウント・課金・独自ドメイン・画像最適化・テンプレート・AI生成・共同編集・SEO設定はスキップ。

## Approaches Considered

### Approach A: Vibe Deploy 週末プロトタイプ（採用）

- HTMLペースト・ZIPドロップ・URL発行・秘密の編集URL上書き・削除のみ
- Cloudflare Workers + R2 + KV
- 開発期間：3〜5日
- 成功条件：同僚さんが来週、創業者に頼らず文言修正を公開できる

### Approach B: AI Publishing Hub フル版

- Aに加えて、Claude.ai/ChatGPT chrome拡張で「このHTMLを公開」ボタン、Discord/Slack bot連携、AI生成エラーの自動説明、"Made with AI" バッジ
- 開発期間：2〜3ヶ月
- 同僚unblockまで時間がかかりすぎ、N=1で判断するには大きすぎる、却下

### Approach C: コンシェルジュMVP（Typeform + 手動デプロイ）

- コードを書かず、Typeformで申込を受けて創業者が手動で月500円のサイト運用を10人提供
- 「人が金を払うか」をゼロコードで検証
- 製品感ゼロ、バイラル余地ゼロ、却下（ただしAに並走させる手はある）

## Recommended Approach

**Approach A** で進める。

理由：

- N=1（同僚さん）の事例とMVPが完全に整合
- Codex/Claude両者の意見が完全一致
- 開発期間3〜5日でN=1検証が完了する最短経路
- 「AIで作ったHTMLを貼るだけで公開」コピーは Twitter / Hacker News でバイラル可能、上振れの余地

## Open Questions

- 編集URLのトークンを忘れた場合の復旧UX（メアド登録？それともUUID秘密保持を強制？）
- 同僚さん以外のAIユーザーをどこで探すか（Claude Code Discord？X上のClaude Codeコミュニティ？）
- 月数千件規模になったときのabuse対策の追加レイヤー（manual moderation queue、自動マルウェア検査）
- カスタムドメインを「ある時点」で出す必要が出た場合、有料化を同時に出すべきか

## Success Criteria

**Phase 1（来週月曜）：** 同僚さんがVibe Deploy上で会社HPを公開し、3日以内に自分でコピー修正を1回成功させる。創業者を経由しない。

**Phase 2（4週間以内）：** 同僚さん以外のAIユーザー10人がアカウントなしで利用、うち3人以上が編集URLで「2回以上」更新する（つまり「使い続ける」）。

**Phase 3（3ヶ月以内）：** 月間アクティブ公開サイト数 100以上、または有料化トライアルで支払い意思を示すユーザー 5人以上。

## Distribution Plan

- Web serviceとして既存パイプライン上で配布（特別なCI/CDは不要、Cloudflare Workersへの `wrangler deploy` のみ）
- 初期ドメイン：Cloudflare の `*.workers.dev` または個人ドメイン（後から独自ドメインへ移行可能）
- 初期マーケティング：(1) 同僚さんに直接渡す、(2) X（旧Twitter）上の Claude Code / v0 コミュニティに「Claude Codeで作ったHTMLを貼るだけで公開できるやつ作った」と投稿、(3) Hacker News Show HN を狙う

## Dependencies

- Cloudflare アカウント、R2 と Workers の有効化
- ドメイン取得（保留可能、最初は `*.workers.dev` でOK）
- 法的整理：ToS（利用規約）と DMCA 対応窓口（最低限の雛形のみ）

## The Assignment（最重要・コードより先にやること）

**コードを書く前に、同僚さんの隣に座って Netlify Drop（<https://app.netlify.com/drop）> を使わせる。手伝うな。横で見ているだけ。**

- 何分で諦めるか測定
- どこで詰まるか書き留める（具体的な画面、ボタン、文言）
- 質問されても答えない。「自分でやってみて」と返す
- 完了したか、完了できなかったかを記録

これが2つの成果を同時に出す：

1. **需要の追加証拠** — 本当にN=1の体験が再現されるかの確認
2. **MVPの仕様** — 同僚さんがどこで詰まるかが、あなたが作るべきUXの正確な仕様書になる

時間目安：30分。これを **コードを1行も書く前に** やる。

## What I noticed about how you think

- あなたは最初の質問で「他の人がAIでHTML/CSSをClaude Codeとかで作っているがそれを公開する手段がなかったようだ」と言った。これは多くの人が見落とすが、**自分自身が現状の解決策である** こと（同僚さんのGitHub Pagesを運用している）を自然に話した。これは founder-as-the-workaround という重要なシグナル、最強の需要証拠の一形態。
- フル仕様（D）を最初に選んだのは典型的な「アーキテクチャに恋している」サイン。だが、Codexが challenge した P5 の修正には素直に同意し、Bを選ばずに A を選んだ。**取り入れる柔軟性** があるということ。
- 提出した7つの質問（Netlify再発明か？差別化は？MVPスコープは？abuse対策は？技術構成は？セグメントは？コピーは？）はすべて **正しい順序** で並んでいた。これは初めての起業ではない、もしくはすでに製品作りの感覚を持っている人の質問。
- 「abuse対策として、最初から最低限入れるべき制限は何か？」を最初の段階で考えた点は taste のサイン。多くの founder は「とりあえず作って公開してから考える」と言う。あなたは制約を最初から織り込もうとしている。
